# CF-I18N-001 — Application-owned typed i18n boundary

Status: `ACCEPTED FOR CF-I18N-ES-AR-001`

## Context

The product requires complete `es-AR` and `en` presentation, Argentine `Intl` formatting, pluralization, persistent runtime language switching, feature namespaces, regression gates and future maintainability. The original scope preferred `i18next`/`react-i18next`, while the first remote task artifact introduced an application-owned typed React context.

Measured at `origin/feature/i18n-es-ar@ef80cf85afc892100c152f622454624377ea5206`, the application-owned foundation builds to 254,992 bytes raw / 75,744 bytes gzip JavaScript and passes the existing 320,000 / 100,000 byte budgets with no added runtime dependencies.

## Options evaluated

### `i18next` + `react-i18next`

- Strongest built-in plural rules, namespace loading and ecosystem interoperability.
- Better default choice if HMS adds several locales, translator tooling, remote catalogs or lazy namespace delivery.
- Typed keys require additional TypeScript augmentation or generation.
- Adds runtime/dependency and supply-chain surface. A local exploration also showed that merely adding the library does not create complete coverage; its DOM compatibility bridge is rejected and remains only on the preserved local salvage branch `feat/i18n-es-ar@d85f2b0`.

### Application-owned typed boundary

- Compile-time `MessageKey` parity and direct React Context/Hook interoperability.
- No runtime dependency or catalog request; resources are bundled once for Cloudflare Static Assets.
- The current two locales share the same cardinal plural categories and can use `Intl.PluralRules` through a small typed API.
- Lower runtime complexity, but physical catalog namespaces and coverage tooling are mandatory to prevent a monolith.
- Less suitable for many languages or external translation workflows.

## Decision

Retain the application-owned typed i18n boundary for this two-locale increment. This is an explicit bounded exception to the library preference, justified by the measured zero-dependency bundle, existing typed foundation and current product scope.

Before Product Acceptance it must:

1. expose typed translation, pluralization and `Intl` formatters through `I18nProvider`/`useI18n`;
2. keep feature catalogs in physical namespace modules rather than one growing file;
3. enforce exact `es-AR`/`en` key parity and reject untranslated UI literals;
4. translate presentation values without changing API/domain values;
5. prove runtime switching, persistence, `<html lang>`, mobile and full Product Flow behavior.

## Adoption triggers for i18next/react-i18next

Re-evaluate and normally adopt when any two apply: a third locale, locale-specific plural categories beyond the current API, translator-managed external resources, runtime/lazy namespace loading, ICU-rich messages, or repeated growth of the application-owned engine beyond its bounded provider/formatter role. Migration remains behind `useI18n`, so feature components do not change API.
