## Outcome

An authorized Reception operator can select a due arrival, complete identity,
stay and room-readiness checks in one focused task, submit the canonical
check-in command, see the authoritative result, and continue with the next
visible case by canonical priority. Search/filter/scroll context survives
refresh, conflict and exit. Desktop and mobile complete the same journey.

## Observed baseline and bounded gap

The current Reception queue is derived from `/bookings`, `/rooms`, `/guests`
with a browser date; all confirmed bookings show edit and check-in forms at
once. The mobile check-in stepper uses `window.innerWidth` in render. Submit
closes the case and reloads the queue without selecting the next case. A 409
is a generic workspace error. The binding V11 front-desk board is absent.
Implement only the read model and UI changes needed for P0.1. Existing
Housekeeping mutations and later P0 workflows remain untouched.

## Backend just-in-time rule

The existing routes do not expose V11 `GET /api/v1/front-desk/board`, which
owns hotel-local queue priority and readiness. This is a demonstrated P0.1
gap. Implement its smallest read-only contract needed for arrival/check-in,
using existing tenant database/capability authority and canonical room,
booking, maintenance truth. Do not create a second lifecycle write path or
financial source. If a stronger domain guard is required to prevent a
truthful blocker from being bypassed at check-in, make only that guard repair
and prove no partial mutation.
